## 飞书智能助手 — 项目需求文档（冻结版 v2.0）

---

### 一、项目概述

**项目名称：** 飞书智能助手（Feishu Smart Agent）

**项目目标：** 构建一个飞书机器人，通过自然语言对话帮助员工快速找到业务流程信息和相关负责人。

**核心价值：**
- 新人入职：快速了解公司流程、规章制度、FAQ
- 全员日常：查找业务负责人、追踪流程进度、定位相关文档

**开发方式：** AI辅助编程  
**技术栈：** Python + FastAPI + lark-oapi SDK（长连接模式） + DeepSeek API

---

### 二、产品形态

| 维度 | 决策 |
|------|------|
| **交互入口** | 飞书单聊机器人（独立对话窗口） |
| **用户群体** | 公司全员 |
| **前端表现** | 统一Bot对话入口，不做功能模块拆分 |
| **回复格式** | 飞书消息卡片（文字说明 + 相关文档链接 + 信息来源引用） |
| **答案置信度** | 多条可能结果 + 明确来源标注，不确定时诚实告知 |
| **权限模型** | 完全继承提问用户本人的飞书数据访问权限（OAuth代用户调用） |
| **响应SLA** | 5-10秒为P95目标；超时必须异步二次回复 |

### 三、核心功能

#### 意图三分类 + 关键词抽取（一体化）

`llm.classify_intent` 调用 LLM 在**同一次**推理里返回 JSON，`core.intent.detect_intent` 负责解析并封装成 `IntentResult(label, keyword, person_hint, raw_question)`。LLM 输出不可解析时降级到规则兜底（关键字判意图 + 噪声词去除），保证流水线不崩。

| 字段 | 作用 | 示例 |
|------|------|------|
| `label` | `find_person` / `search_knowledge` / `chitchat` | `find_person` |
| `keyword` | 用于飞书全文搜索的核心名词短语（已去"找谁/怎么办/吗/的"等疑问词与虚词） | `安全问题` |
| `person_hint` | 问题里显式出现的人名候选，仅 find_person 用 | `张三` |

**为什么必须做关键词抽取**：飞书文档/消息搜索是多 token AND 匹配，长问句（如"安全问题找谁处理"）会被拆成 `["安全","问题","找","谁","处理"]`，疑问词把相关度稀释到阈值以下导致 0 命中；抽取成 `安全问题` 后能稳定命中。

| 意图 | 触发语义 | 对应流水线 |
|------|----------|------------|
| `find_person` | 找人/事物归属/"谁负责"/"归谁管"/"找谁对接" | 四步找人流水线 |
| `search_knowledge` | 查流程/制度/SOP/规范/"XX 是什么"/"怎么做" | 五步知识问答流水线 |
| `chitchat` | 纯问候、闲谈、与业务无关 | 静态能力说明，不调任何 API |

#### 功能1：业务负责人查找（find_person，四步）

用户问事物流程归属/找负责人时，按以下顺序执行（短路+补充语义：前一级命中并不截断后续步骤，LLM 统一整合产出结论）：

```
① 通讯录匹配（contact_client.search_user）
    入参优先使用 intent.person_hint（没人名时回落 keyword）
    ↓ 命中时收集候选 open_id 列表
② 文档搜索（并发两路，均用 intent.keyword）
   - 主查：search_docs(keyword)
   - 有候选人：search_docs(keyword, owner_ids=候选)
    ↓ 合并去重后作为候选人相关文档
③ 群聊消息搜索（search_messages, group_only=True，用 intent.keyword）
    ↓ 找人场景强制仅群聊，不含私聊
④ LLM 推理整合（synthesize_person）
   输入：通讯录候选 + 文档命中 + 群聊消息命中（含正文+sender）
   输出：最可能负责人 + 关键依据 + 补充线索
```

#### 功能2：知识问答 / 专题总结（search_knowledge，主链路）

用户问流程、制度、政策、知识点，或问“我们组是干什么的 / 主要负责什么 / 工作流程是什么”这类专题归纳问题时，统一进入 `search_knowledge` 主链路。但链路内部会先做 **LLM 前置语义标注**，再决定是走普通问答还是 summary 归纳模式。

核心原则：
- 先让 LLM 分析问题，不直接回答
- 再运行检索代码
- 最后由 LLM 基于检索结果归纳总结
- 总结时优先依托文本事实；如果文本没有直接写明，但实体相关技术文档已体现系统用途、输入输出、服务对象、上下游关系，则允许做“基于现有文档的审慎推测”

当前执行顺序：

```
① 前置语义标注（LLM routing）
   - 输出 keyword / keyword_fallback / aliases / intent_focus / preserve_entities / clarify_options
   - summary_mode 判定 = 命中总结触发词 OR routing.intent_focus == "summary"

② query 构造
   - 基于 keyword + fallback + aliases + LLM 扩词生成 query candidates
   - 若为 summary 场景，优先把 preserve_entities 注入检索
   - 若问题里出现“我们组 / 本组 / 我们团队”且 preserve_entities 为空：
     a. 优先从最近会话继承实体（如 CVAT / SUST / 数据标注）
     b. 若仍继承不到，则不再硬搜泛词，直接进入澄清引导

③ 多源检索
   - 知识库搜索（search_wiki → /open-apis/wiki/v2/nodes/search，命中 doc/docx 时补拉正文）
   - 云文档搜索（search_docs(keyword) + 按 docs_type 拉正文）
   - 多维表格搜索（search_bitable(keyword) + list_tables + search_records）
   - 聊天记录搜索（search_messages(keyword)，沿用全局 include_p2p_message_search 开关）

④ 证据整理
   - context 按“知识库 → 云文档 → 多维表格 → 聊天记录”顺序拼接，并带 `[来源：xxx]`
   - 长内容先做证据摘要，再进入最终回答/总结
   - summary 模式限制单轮正文拉取预算，优先保留正文质量更高的文档

⑤ LLM 输出
   - 普通知识问答：生成基于证据的 RAG 回答
   - 专题总结：围绕流程、核心业务、协作关系做结构化归纳
   - 若实体相关材料不足以支持确定性结论，但足以体现系统作用和协作关系，可明确写成“根据现有文档判断/推测”

⑥ 结果自检（LLM self-check）
   - 检查答案是否真的被证据支撑
   - 检查是否只是命中了泛词、模板文档或弱相关材料
   - 必要时降级为更谨慎表述，或改为“请补充组名 / 项目名 / 系统名”
```

补充说明：
- summary 触发词已覆盖口语表达，如“干什么”“干什么的”“主要负责什么”“主要做哪些事”
- 对“我们组是干什么的”这类问题，系统默认把它视为“团队职责归纳”问题，而不是普通定义问答
- 如果没有任何上下文实体，也没有足够组别线索，卡片会优先引导补充信息，而不是继续包装成弱答案

#### 功能3：闲聊/兜底（chitchat）

对纯问候或与业务无关的问题，直接返回能力说明文案，不触发任何授权校验和检索调用，延迟最低。

#### 功能4：消息搜索范围开关

为满足隐私与可控性，消息检索支持开关策略：
- 找人场景强制仅群聊（`group_only=True`，私聊不参与找人）
- 知识问答场景沿用全局 `include_p2p_message_search` 开关
- 回复卡片中会明确提示"本次检索范围"

### 七、用户交互流程（冻结）

#### 首次使用（OAuth）

1. 用户首次发送消息  
2. Bot提示授权并发送OAuth卡片  
3. 用户确认授权  
4. Bot提示授权成功，进入正常问答

#### 正常问答（长连接模式）

1. 用户发送消息  
2. 飞书通过 WebSocket 长连接推送事件到你的服务  
3. 事件处理函数立即发送确认文本：`收到，正在为您查找…`  
4. 启动异步任务执行检索与LLM整合（目标5-10秒）  
5. 任务完成后，Bot主动发送最终结果卡片

#### 超时处理（必须）

- 若后台处理超过10秒仍未完成：先发送中间提示  
  `查询比较复杂，请稍等…`
- 后台继续执行，完成后再发送最终结果卡片（异步二次回复）

### 八、错误处理

| 场景 | Bot回复策略 |
|------|-------------|
| 未授权用户 | 引导授权并发送授权链接 |
| 授权过期 | 提示重新授权 |
| 未找到信息 | 提示补充更多业务细节；若是“我们组/本组”类 summary 问题，优先引导补充组名、项目名或系统名 |
| API调用超时 | 先发中间提示，后异步补发结果或失败说明 |
| LLM无法确定 | 若有实体相关证据，则明确标注“根据现有文档判断/推测”；若缺少组别线索，则优先返回澄清引导 |
| 权限不足（可见标题不可读内容） | 返回文档标题，不返回内容片段 |
| 非业务问题/闲聊 | 意图识别归为 `chitchat`，直接返回能力说明文案，不触发检索/授权 |

#### 目录（文件夹）职责说明

| 目录 | 做什么 | 备注 |
|------|--------|------|
| `api/` | FastAPI 路由层（目前主要是 OAuth callback） | 只做“入口/协议适配”，不放业务编排 |
| `core/` | 业务核心编排与流水线（意图→检索→LLM→卡片） | 你要改“机器人回答逻辑”，大多在这里 |
| `feishu_client/` | 飞书 OpenAPI 访问封装（tenant/user 两种身份） | 所有飞书 HTTP 调用集中在这里，便于统一处理错误码与重试 |
| `llm/` | LLM 调用与 Prompt 管理 | 意图识别、找人合成、RAG 回答都从这里出入口 |
| `utils/` | 横切能力：日志、缓存、HTTP 连接复用、token 落盘、会话存储 | 通常不含业务规则 |
| `.tokens/` | OAuth 用户态 token 的本地持久化 | 运行产物，包含敏感信息，不提交 git |
| `.memory/` | 会话/话题/历史的本地存储（SQLite） | 运行产物，不提交 git |
| `.venv/` / `.venv*/` | Python 虚拟环境 | 运行/开发产物，不提交 git |

> 说明：如果目录里出现 `Lib/`、`Scripts/`、`__pycache__/` 等，一般也是虚拟环境或运行产物，应保持不提交 git（以 `.gitignore` 为准）。

### 十一、关键技术决策（冻结）

| 决策点 | 选择 | 备注 |
|--------|------|------|
| 后端框架 | Python + FastAPI | FastAPI仅用于健康检查与OAuth回调 |
| 消息接收方式 | 飞书长连接（WebSocket） | 无需公网地址，本地开发友好 |
| 飞书SDK | `lark-oapi` | 官方SDK，内置长连接客户端 |
| LLM | DeepSeek API | 统一用于意图和回答生成 |
| 部署方式 | 任意可联网机器 | 长连接模式下无需公网可达 |
| 缓存策略 | 内存缓存 | 接受多实例缓存不一致 |
| 文档能力 | 新旧版文档 + docs搜索 + wiki | 首版全做 |
| 消息能力 | 搜索API + 用户权限继承 | 支持私聊，可配置开关 |
| 回复策略 | 飞书消息卡片 | 非纯文本 |
| 时延策略 | P95 5-10秒 | 超时必须异步二次回复 |
| 知识链路策略 | 前置标注 + 检索 + 总结 + 自检 | summary 支持文本优先、证据约束下的审慎推测 |

当前项目是一个基于飞书长连接模式运行的企业智能助手，核心目标是：

- 在证据不足时给出更谨慎的回答或引导补充信息

当前系统已经不是最初的“简单问答机器人”，而是一个包含以下能力的企业检索代理：

- 飞书消息长连接接收
- 多源检索
- LLM 意图识别
- 找人链路整合
- 知识检索链路前置标注、总结和自检
- 会话上下文记忆
- 消息卡片化输出

#### 15.2 当前实际架构总览

当前项目运行时由 5 层组成：

1. 飞书接入层
2. 事件编排层
3. 业务流水线层
4. LLM 能力层
5. 本地状态与持久化层

可按下面理解：

```text
飞书消息事件
-> 长连接客户端接收
-> 事件编排与去重
-> OAuth 校验
-> 意图识别 / 问题改写
-> 按意图进入找人 / 知识检索 / 闲聊 / 图片分析
-> 多源检索 + LLM 总结 / 自检
-> 卡片格式化
-> 飞书消息发送
```

#### 15.3 关键模块说明

##### `main.py`

项目启动入口，负责：

- 启动 FastAPI

这是整个服务的启动总控。

##### `feishu_client/ws_client.py`

负责飞书长连接接入，核心职责：

- 使用 `lark-oapi` 长连接 SDK 接收飞书事件
- 在独立工作线程中运行 SDK
- 把消息事件和卡片动作投递回主事件循环
- 将消息交给 `core/event_handler.py`

当前系统不是通过公网 Webhook 收消息，而是通过长连接方式收消息。

##### `api/oauth.py`

负责 OAuth 授权相关逻辑，核心职责：

- 提供授权地址接口

- 调用飞书换取用户 token
- 在授权成功后恢复用户之前待处理的问题

这是用户权限链路的关键入口。

这是当前系统最重要的编排模块之一，负责：

可以把它理解为整个机器人的“总调度器”。

##### `core/intent.py`

#### 15.7 当前已确认的主要问题

当前系统可以运行，但还存在几个关键问题。

##### 1. 找人链路回答不够精准

典型表现：

- 命中了材料，但回答还是不具体
- 泛词问题容易命中很多噪声
- 文档、群聊、通讯录的证据优先级还不够稳定
- 相近问法的 query 不够稳定

##### 2. 流程查询问题跨文档时不够强

典型表现：

- 用户问流程节点该找谁时，答案不一定能准确落到当前步骤责任人
- 文档之间存在引用关系，但系统没有充分利用这些关系
- 普通向量 / 关键词检索对“流程 + 责任人”这类问题解释力不够强

##### 3. 通用知识检索仍然会受到泛词影响

典型表现：

- 用户问题较泛时，query 易被稀释
- 材料搜到了，但未必真正回答问题
- 需要更多“问题理解 -> 检索 -> 自检”的稳定闭环

#### 15.8 当前已经形成的方案结论

这一轮对话中，已经明确形成了以下方向性结论：

##### 结论一：短期不引入 Obsidian 作为前置条件

原因：

- 当前主要问题是检索精度和关系利用不足
- 不是知识编辑工具缺失
- 引入 Obsidian 会扩大项目范围，但短期不一定直接提升效果

因此当前结论是：

- 轻量图不依赖 Obsidian
- 先基于现有飞书数据源做关系增强
- 后续若需要长期治理知识结构，再考虑 Obsidian 作为知识编辑层

##### 结论二：后续更适合做轻量 GraphRAG，而不是重型知识图谱

已经明确推荐的方向是：

- `Hybrid Retrieval`
- `别名归一`
- `文档引用关系`
- `人-流程-文档` 轻量关系建模
- `1 跳图扩展`
- `rerank`

而不是一上来做：

- 全量知识图谱平台
- 重型图数据库优先
- 复杂多跳推理

##### 结论三：当前项目适合做“中改增强”，不适合“大改重构”

已经明确判断：

- 不需要推翻现有项目重做
- 可以在现有 `find_person` 和 `search_knowledge` 上加一层轻量关系增强
- 第一阶段先聚焦“找人 + 流程查询”

#### 15.15 当前一句话总结

当前项目已经具备完整可运行的企业检索助手雏形，核心基础设施已经齐全，下一阶段不应该推翻重做，而应在现有架构上优先完成 Ubuntu 环境迁移，并围绕“找人 + 流程查询”做轻量关系增强和精度提升。
- 不再需要公网 URL 和 ngrok
- FastAPI 角色从"主要服务"变为"仅用于健康检查与OAuth回调"
- 新增 `core/event_handler.py`，移除 `api/webhook.py`
- 目录结构、架构图、依赖清单、后台配置清单均已同步更新
- 所有功能、权限、交互流程、错误处理保持不变

**变更说明（v2.0 → v2.1）：** 按最终架构图对齐意图路由与两条检索流水线
- 意图识别：四类（find_person / search_knowledge / mixed / unsupported）→ 三类（find_person / search_knowledge / chitchat），解析失败默认兜底 `chitchat`
- 找人流水线：由原先的「并列三源 + 简单拼接」升级为四步流水线（通讯录 → 文档含 owner_ids 补查 → 群聊消息 → LLM 推理整合），私聊不再参与找人（`group_only=True`）
- 查知识流水线：由原先的三源升级为五步流水线，顺序调整为 **知识库 → 云文档 → 多维表格 → 聊天记录 → LLM 生成**；知识库入口由之前的 `list_spaces`（列空间）替换为 `search_wiki`（搜节点），修复"只列不搜"的逻辑 bug
- 新增 `core/chitchat.py`，闲聊分支静态返回能力说明且不触发 OAuth 授权校验
- `feishu_client/search.py` 扩展：`search_docs` 新增 `owner_ids`，`search_messages` 新增 `group_only`，新增 `search_wiki`
- `llm/prompts.py` 新增 `PERSON_SYNTHESIS_PROMPT`，`llm/client.py` 新增 `synthesize_person` 方法

**变更说明（v2.1 → v2.2）：** 意图识别与关键词抽取合并，修复长问句搜索 0 命中问题
- 观察到：`"安全问题"` 能命中文档/消息/知识库/多维表格，但 `"安全问题找谁"` / `"安全问题找谁处理"` 全部 0 命中。根因是飞书搜索是多 token AND 匹配，`找/谁/处理` 把相关度稀释到阈值以下
- `llm/prompts.py` 的 `INTENT_PROMPT` 改为单次调用输出 JSON：`{intent, keyword, person_hint}`，不增加额外 LLM 调用
- 新增 `core.intent.IntentResult` dataclass；`detect_intent` 负责 JSON 解析 + 二次去噪；LLM 输出不可解析时规则兜底
- 下游签名调整：`run_find_person(open_id, intent)` / `run_search_knowledge(open_id, intent)`；所有搜索 API 改用 `intent.keyword`，通讯录优先使用 `intent.person_hint`
- 兼容用例：`"安全问题找张三"` → 通讯录用 `张三`、文档/消息用 `安全问题`；`"办公室问题该找谁"` → 全部用 `办公室问题`

**变更说明（v2.2 → v2.3）：** 稳定性、可观测性与细节打磨
- `feishu_client/base.py` 新增 `FeishuApiError`（保留 `code/msg/data`），`request_as_user` 识别 `99991661/99991662/99991664/99991672/20006` 等"用户 token 失效/被撤销/无权限" code，自动 `user_token_store.delete` 并抛 `PermissionError`，让上层走授权卡片分支重新走 OAuth
- `core/intent.py` 放弃贪婪 regex `{.*}`，改用 `json.JSONDecoder.raw_decode` 遍历第一个 `{` 起点直到找到合法 JSON，能正确处理"LLM 在前后加解释文字 / 返回多个 JSON 片段"场景
- `core/intent.py` 增加保护：非 chitchat 意图但 `keyword` 与 `person_hint` 都为空时降级为 chitchat，避免退回到"整段长问句喂搜索"的稀释状态
- `core/search_knowledge.py` 的 `_step_messages` 引入 `message_client.fetch_messages_text`，不再只把 `message_id` 列表丢给 LLM，而是拉正文（单条限 300 字）让 LLM 能真的引用消息内容
- `core/find_person.py` 构造 `open_id → name` 映射，`_format_docs` / `_format_messages` 把文档 owner、消息 sender 的 `open_id` 优先展示成可读姓名，帮助 LLM 跨素材关联
- `utils/cache.py` 的 `MemoryCache` 加 `threading.Lock`，加 `delete` 方法：ws 线程回调和 asyncio 主线程并发读写 `_store` 更安全
- `feishu_client/ws_client.py` 在 `_run_ws_blocking` 的 `try/finally` 中 `worker_loop.close()`，类型签名 `event_fn: Callable[[Any], None]`
- `main.py` 从弃用的 `@app.on_event("startup"/"shutdown")` 迁移到 FastAPI `lifespan` 异步上下文，同时在启动阶段预热 `user_token_store`（打印恢复了多少用户）
- 删除无调用方的 `feishu_client/knowledge.py`（`list_spaces` 已被 `search_wiki` 取代）

**变更说明（v2.3 → v2.4）：** 修掉"搜到了但 LLM 看不到正文"的 false negative，RAG 召回系统性升级
- 背景：`find_person` 分支能搜到含"OA 审批事务找张三"的云文档（`docs_main=2`），但最终输出"未命中"——根因是 `_step_docs` / `_format_docs` 只把标题和 `owner_id` 喂给 LLM，完全没拉文档正文
- `core/find_person.py` 新增 `_enrich_docs_with_raw`：对命中文档的 top 3 并发拉 `get_docx_raw_content`，失败兜底老版 `get_doc_raw_content`；整批 4s 超时保护；`_format_docs` 把前 600 字正文打到 LLM context
- `core/search_knowledge.py` 的 `_step_wiki` 对 `obj_type in {"docx","doc"}` 的节点同步拉正文（4s 并发超时），非 docx 节点仍保留 title+url
- `feishu_client/bitable.py` 新增 `search_records`（`POST .../records/search`，用户态复用 `base:record:retrieve`，无需加权限）；`core/search_knowledge._load_bitable_context` 重写：遍历每个命中 bitable 的所有表（上限 5 张），对每张表的 50 条记录做本地 substring 关键字过滤，命中行附带表名喂给 LLM，彻底替代旧版"盲拉第一张表前 5 条"
- `llm/prompts.py` `INTENT_PROMPT` schema 增加 `keyword_fallback` 字段（更短/更宽的备用关键词）；`core/intent.IntentResult` 同步新增字段并在规则兜底分支给出 2 字截断 fallback
- `core/find_person.py` / `core/search_knowledge.py` 主关键词零命中时，统一用 `keyword_fallback` 整轮重试一次（不做每源双搜，避免翻倍请求）；`sources` 里会明确记录"使用备用关键词 xxx 重试命中"
- `core/event_handler.py` 新增 60s 结果缓存（`(open_id, normalized_text)` 级别）：命中直接下发历史答复并带"(来自 60s 结果缓存)"标记，跳过意图分类 / 搜索 / LLM；`PermissionError` 和其它异常场景不写缓存
- `core/find_person.py` / `core/search_knowledge.py` 新增素材全空短路：通讯录 + 文档 + 消息（或四源 context）全零命中时，直接返回固定话术，不再调用 LLM，省 1-2s 且杜绝幻觉
- `llm/prompts.py` `PERSON_SYNTHESIS_PROMPT` 加硬约束：`open_id` / 文档标题 / `sender_id` 不得当人名，无明确中文人名时必须回"暂无明确候选"
- `config.py` `processing_timeout_seconds` 由 6 改为 8，减少普通查询（搜索 3s + LLM 4s）就触发"查询比较复杂…"interim reply 的噪音

**变更说明（v2.4 → v2.5）：** 全局引入“前置标注 + 检索 + 自检”闭环，知识链路支持专题总结
- `core/find_person.py` 接入 LLM 前置语义标注与结果自检，形成“路由 → 检索 → 综合回答 → 自检降级”闭环
- `core/search_knowledge.py` 同步接入知识链路的 routing / self-check，普通问答与 summary 共用同一前置语义标注能力
- `llm/prompts.py` 新增 `PERSON_ROUTING_PROMPT`、`PERSON_SELF_CHECK_PROMPT`、`KNOWLEDGE_ROUTING_PROMPT`、`KNOWLEDGE_SELF_CHECK_PROMPT`
- `llm/client.py` 新增 `route_find_person`、`self_check_person_answer`、`route_search_knowledge`、`self_check_search_answer`
- `core/event_handler.py` 与 `utils/cache.py` 增加重复消息防重：按 `message_id` 去重，并对“同一用户 + 同一文本”处理中防重复，减少重复回复和 token 浪费

**变更说明（v2.5 → v2.6）：** summary 链路增强，支持“我们组是干什么的”这类广泛问题
- `core/search_knowledge.py` 的 `summary_mode` 判定升级为：命中总结触发词，或 `routing.intent_focus == "summary"` 任一成立即进入 summary
- summary 触发词补充自然口语表达：`干什么`、`干什么的`、`主要负责什么`、`主要做什么`、`主要做哪些事`
- `TOPIC_SUMMARY_PROMPT` 与 `KNOWLEDGE_SELF_CHECK_PROMPT` 放宽为“文本事实优先；若实体相关文档可体现系统作用/上下游，可做审慎推测”，但必须显式写成“根据现有文档判断/推测”
- routing 产出的 `preserve_entities`（如 `CVAT`、`SUST`）会真实注入 summary query candidates，并传入 `topic_summary(...)`
- 当问题里出现“我们组 / 本组 / 我们团队”且 `preserve_entities` 为空时，系统会先尝试从最近会话继承实体；继承不到则优先澄清，而不是拿“主要任务 / 工作内容”这类泛词硬搜到底
- 结果卡片新增“需补充信息”“最近上下文实体”等提示；在澄清场景下压掉误导性的泛词重试按钮，优先引导用户补充组名、项目名或系统名
- search_knowledge 的 summary 结果仍经过自检：证据足够时正常归纳；证据不足但可做实体约束推测时输出“判断/推测”；如果缺少组别线索则直接引导澄清
