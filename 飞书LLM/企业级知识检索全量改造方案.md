# 找人链路专项改造方案

## 1. 文档目的

本文档用于沉淀当前飞书企业助手项目在 `find_person` 模块上的专项改造方案。

本期改动目标只有一个：

- 增强找人链路的检索命中率与回答准确度。

本期采用的核心方法只有一个：

- 让 LLM 在找人链路中承担“前置语义标注 + 检索后证据总结 + 最终自我校验”的闭环角色。

本期明确不做以下事情：

- 不重写知识问答链路。
- 不扩展新人引导专线。
- 不引入会改变现有整体检索框架的大规模新架构。
- 不重做全局权重体系。
- 不改变当前项目的核心入口、OAuth、会话、卡片和消息发送机制。

本文档只关注找人模块的业务逻辑、检索逻辑、提示词逻辑和实现边界，便于后续围绕该模块单独对接需求与实施。

---

## 2. 本期边界

### 2.1 改动范围

本期只允许改动以下内容：

- `core/find_person.py`
- `core/intent.py` 中与找人问题相关的关键词抽取和 query 收敛逻辑
- `llm/prompts.py` 中与找人综合判断相关的 prompt
- `core/formatter.py` 中与找人卡片展示相关的少量文案
- `core/card_actions.py` 中与找人卡片重试、澄清相关的少量动作

### 2.2 不改范围

以下部分本期保持现状：

- `core/search_knowledge.py`
- 知识问答四源检索逻辑
- summary 模式十篇限制逻辑
- 通识问答逻辑
- 新人引导链路
- 会话数据库结构
- OAuth 与 token 存储

### 2.3 核心约束

本期所有改动都必须满足以下约束：

- 只增强找人链路，不影响其他检索逻辑。
- 不改变知识问答当前行为。
- 不改变现有项目的主调用链路。
- 不引入新的统一数值打分框架替换现有逻辑。
- 权重口径必须和当前找人业务原则一致。
- LLM 负责理解、标注、总结和校验，代码负责检索执行、数据源限制和证据优先级控制。

## 3. 当前找人链路现状

### 3.1 当前主流程

当前找人链路主流程在 `core/find_person.py` 中，整体逻辑如下：

1. 根据 `intent.person_hint` 或 `intent.keyword` 查通讯录
2. 生成找人 query 候选词
3. 并发检索文档、知识库、群聊
4. 合并命中结果
5. 拉取文档正文
6. 过滤消息与文档
7. 交给 LLM 综合判断“找谁”

### 3.2 当前已经符合业务的地方

- 不搜私聊
  - 当前群聊搜索已经是 `group_only=True`
- 找人链路独立于知识问答链路
- 文档正文已经会被拉取并进入 LLM 综合判断
- query 已有一定收敛逻辑

### 3.3 当前主要问题

当前找人链路在大型机器人企业场景下，主要存在以下问题：

- 泛词问题过多
  - 例如 `IT`、`IT相关事务`、`设备问题`、`安全问题`
- 相近问题命中的 query 不稳定
  - 同一类问题，有时落到 `IT`，有时落到 `IT维修`
- 文档优先原则尚未完全固化
  - 目前工程上文档更重，但 LLM 证据优先级仍需进一步明确
- 群聊噪声较高
  - 对大企业来说，群聊中泛词过多，容易污染负责人判断
- 通讯录弱命中容易造成误导
  - 通讯录可以提供候选人，但不应单独决定负责人

### 3.4 当前最适合的改造方式

基于现有项目状态，本期最适合的方案不是重写检索框架，而是在现有 `find_person` 流程上插入一个轻量闭环：

1. 第一次 LLM 推理
   - 负责理解问题，完成职责域归并、同义词归并、泛词识别和 query 标注
2. 代码执行检索
   - 仍然按当前找人链路检索通讯录、文档、知识库、群聊
3. 第二次 LLM 推理
   - 基于检索证据输出找人结论
4. 第三次 LLM 校验
   - 对前后两次推理和检索结果做一致性检查，必要时降低结论强度

这个方案的优点是：

- 改动集中在找人模块
- 不影响知识问答
- 能利用成熟模型的语义归并能力
- 又不会把最终执行权完全交给模型

## 4. 本期改造目标

本期目标不是“把找人链路推翻重做”，而是在现有框架上做精准增强。

### 4.1 目标一：让泛词问题先收敛再检索

例如：

- `IT相关事务找谁`
- `设备问题找谁`
- `安全问题找谁`

这类问题不能直接按裸词搜，而应先收敛到更具体的问题域。

### 4.2 目标二：让相近问法落到更稳定的 query

例如以下问题，应尽量进入同一问题域：

- `IT维修找谁`
- `IT相关的事找谁`
- `IT报修找谁`
- `电脑维修找谁`

### 4.3 目标三：把“文档优先、群聊补充”写死成明确规则

对你当前业务来说，找人问题必须遵循：

- 文档 / 知识库正文是主依据
- 群聊消息是补充依据
- 通讯录是候选线索
- 不使用多维表格
- 不使用私聊

### 4.4 目标四：减少命中很多但回答不具体的情况

当前存在“明明搜到一些材料，但回答还是不具体”的问题。

本期需要改善：

- 结果材料的有效性判断
- 泛词命中的降噪
- 更具体 query 的优先使用

### 4.5 目标五：形成同一上下文下的闭环自检

本期方案要避免“模型前后两次推理彼此割裂”的问题。

因此，找人链路中的前置理解、检索后总结和最终校验，必须共享同一个结构化上下文。

这样可以实现：

- 前置语义标注与最终答案保持同一职责域
- 检索前后的 query 口径一致
- 最终结论可回看前置判断是否被检索结果推翻
- 当证据不足时，自动降级为“主推荐 + 备选”或“请补充信息”

## 5. 本期业务原则

这是本期实施必须严格遵守的业务规则。

### 5.1 数据源原则

找人链路只使用以下四类数据源：

- 通讯录
- 云文档
- 知识库
- 群聊消息

明确不使用：

- 多维表格
- 私聊消息
- 通识问答

### 5.2 证据优先级原则

找人问题的证据优先级固定为：

1. 文档 / 知识库正文中明确写明的负责人、接口人、职责归属
2. 群聊正文中明确出现的“找谁”“谁负责”“联系谁”
3. 通讯录命中的候选人
4. 文档 owner_id、消息 sender_id 等弱线索

### 5.3 泛词处理原则

以下类型问题，不应直接用裸词回答：

- `IT`
- `设备`
- `安全`
- `事务`
- `问题`

必须通过 query 收敛或澄清，把问题落到更具体的业务子域。

### 5.4 回答原则

- 能明确给出负责人时，直接给出主联系人和依据
- 不能唯一确定时，给出主推荐 + 备选 + 依据
- 如果只有泛材料，没有明确负责人线索，不要硬编具体人名
- 若材料不足，明确告诉用户应补充什么信息

## 6. 本期改造重点

### 6.1 Query 收敛

本期最重要的增强点，是优化找人场景的 query 收敛规则。

目标是让问题先收敛到“职责域”，再进入搜索。

示例：

- `IT相关事务`
  - 优先收敛到：`IT支持`、`IT维修`、`IT报修`、`IT故障处理`
- `设备问题`
  - 优先收敛到：`设备维修`、`设备报修`、`现场设备故障`
- `权限问题`
  - 优先收敛到：`账号权限`、`系统权限`、`软件安装权限`

### 6.2 Query 稳定化

对于语义接近的问题，候选 query 的排序要更稳定。

例如 `IT相关事务找谁` 和 `IT维修找谁`，不应该一个最终落到 `IT`，另一个落到 `IT维修`，导致回答差异过大。

本期要做的是：

- 减少裸英文词在找人场景中的优先级
- 提高“英文 + 中文职责词”的优先级
- 将企业术语别名统一收敛到固定职责域

### 6.3 文档优先落地

虽然当前代码中已经会拉文档正文，但本期需要进一步把“文档优先”固化在找人 prompt 和筛选逻辑里。

具体要求：

- 文档 / 知识库出现明确职责时，优先采用
- 群聊不能轻易覆盖文档中的明确结论
- 群聊只在文档没写明时，才作为补充依据

### 6.4 泛词降噪

对大企业来说，像 `IT`、`安全` 这类词容易命中大量噪声材料。

本期需要：

- 降低裸泛词作为最终 `effective_query` 的概率
- 更依赖具体 query 命中
- 保留更具体 query 的优先级

### 6.5 LLM 语义标注层

本期方案的主思路，是在找人链路里新增一个 `LLM 标注层`。

它的职责不是直接回答“找谁”，而是给用户问题做轻量结构化标注，包括：

- 标准职责域
- 同义词归并
- 候选扩展 query
- 是否属于泛词
- 是否需要澄清

示例输出：

```json
{
  "canonical_domain": "IT维修",
  "aliases": ["IT报修", "电脑维修", "设备故障处理"],
  "fallback_domain": "IT支持",
  "is_ambiguous": false,
  "need_clarification": false
}
```

如果问题较模糊，则输出：

```json
{
  "canonical_domain": "IT相关事务",
  "aliases": [],
  "fallback_domain": "IT支持",
  "is_ambiguous": true,
  "need_clarification": true,
  "clarify_options": ["IT维修", "账号权限", "网络/VPN", "软件安装"]
}
```

代码侧只把这些结果用于：

- 收敛 `search_key`
- 生成更稳定的 query candidates
- 控制是否需要澄清

代码侧不直接把这些标注结果当成最终负责人结论。

## 7. 找人链路目标流程

本期不改变主流程框架，只增强每一步的质量。

目标流程如下：

```text
用户问题
-> intent 识别为 find_person
-> 第一次 LLM 推理：语义标注与职责域归并
-> 提取 search_key / keyword_fallback / person_hint
-> 生成 query candidates
-> 对候选 query 做找人专用排序
-> 依次尝试 query
-> 并发检索通讯录、文档、知识库、群聊
-> 优先使用更具体 query 的命中
-> 拉文档正文
-> 按 effective_query 过滤文档和消息
-> 第二次 LLM 推理：按“文档优先、群聊补充”综合判断
-> 第三次 LLM 推理：同上下文自检
-> 返回主联系人 / 备选 / 依据
```

这条流程与当前实现保持兼容，不引入新的独立执行框架。

### 7.1 闭环中的共享上下文

为了避免三次推理各说各话，本期方案要求它们共享同一份结构化上下文。

建议上下文字段包括：

```json
{
  "raw_question": "IT相关事务找谁",
  "canonical_domain": "IT维修",
  "aliases": ["IT报修", "电脑维修", "设备故障处理"],
  "is_ambiguous": false,
  "queries": ["IT维修", "IT报修", "电脑维修"],
  "contacts": [],
  "docs": [],
  "messages": [],
  "draft_answer": {
    "primary": "",
    "alternative": [],
    "reason": ""
  }
}
```

第一次推理负责补全前半部分。

检索阶段负责写入 `contacts / docs / messages`。

第二次推理负责写入 `draft_answer`。

第三次推理只负责检查：

- 最终答案是否和 `canonical_domain` 一致
- 是否存在文档支持
- 是否被泛词命中误导
- 是否应该降级输出

## 8. 提示词改造方案

### 8.1 本期只改找人 Prompt

本期不拆全局 prompt 体系，只改 `find_person` 相关 prompt。

本期实际需要 3 个找人相关 prompt 角色：

1. 前置标注 Prompt
2. 证据总结 Prompt
3. 自检 Prompt

### 8.2 Prompt 必须表达的规则

找人综合 prompt 中必须明确写入以下原则：

- 文档 / 知识库正文中的明确职责归属优先于群聊消息
- 群聊消息只能作为补充依据
- 通讯录命中只是候选，不等于负责人
- owner_id / sender_id 只是弱线索
- 如果证据不足，不要编造具体负责人
- 如果无法唯一确定，应输出“主推荐 + 备选 + 原因”

### 8.3 三段式 Prompt 分工

#### 前置标注 Prompt

负责：

- 识别职责域
- 做同义词归并
- 判断是否需要澄清
- 输出标准检索词

#### 证据总结 Prompt

负责：

- 基于检索证据给出主联系人
- 给出备选
- 给出依据
- 判断当前结论强弱

#### 自检 Prompt

负责：

- 检查最终答案和职责域是否一致
- 检查是否有足够文档 / 知识库支持
- 检查是否只是群聊弱线索支撑
- 必要时把结论降级

### 8.4 Prompt 输出目标

当前项目不要求 LLM 严格输出复杂 JSON，可继续保留自然语言答案，但答案结构应更稳定。

建议答案结构：

- 结论
- 依据
- 备选
- 建议补充信息

### 8.5 自检输出建议

自检阶段不需要输出最终面向用户的大段文案，只需要输出一个简洁判断结果即可，例如：

```json
{
  "consistency_ok": true,
  "evidence_strength": "medium",
  "should_downgrade": false,
  "should_ask_more": false,
  "risk_note": ""
}
```

如果 `should_downgrade=true`，则最终对用户的输出应从“唯一负责人”降级为：

- 主推荐 + 备选
- 或提示继续补充部门、项目名、系统名

## 9. 权重与优先级口径

本期不引入新的统一数值评分体系。

不做的事情：

- 不新建全局 100 分制评分器
- 不重写 source weight 计算引擎
- 不替换现有合并和过滤主逻辑

本期采用的仍然是当前业务权重口径，只把它写得更明确：

- 更具体的 query 优先于更泛的 query
- 文档 / 知识库正文优先于群聊
- 群聊优先于通讯录弱线索
- 通讯录优先于 owner_id / sender_id
- 前置标注得到的标准职责域优先于原始裸泛词
- 自检结论可以降低回答强度，但不能凭空提高弱证据的权重

这是一组业务规则，不是新的算法评分表。

## 12. 验收标准

### 12.1 稳定性

以下相近问题，结果不应出现明显方向漂移：

- `IT维修找谁`
- `IT相关事务找谁`
- `IT报修找谁`
- `电脑维修找谁`

预期是：

- 问题域尽量稳定收敛
- 不再频繁掉回裸 `IT`

### 12.2 文档优先

对同一问题：

- 如果文档有明确负责人，回答应优先依据文档
- 群聊只能补充，不应轻易覆盖文档结论

### 12.3 无幻觉

当材料不足时：

- 不要编造具体负责人
- 要明确提示用户补充部门、项目名、系统名或更具体职责词

### 12.4 业务一致性

本期验收必须满足：

- 不搜私聊
- 不用多维表格
- 不触发通识问答
- 不影响知识问答原逻辑

### 13.3 正式职责依据

- 接口人清单

### 13.4 群聊可用范围

## 15. 分阶段规划

在当前找人专项已经验证可行的基础上，后续可以把这套 `LLM 前置标注 -> 检索 -> 总结 -> 自检` 闭环方法逐步扩展到其他链路。

但推进节奏必须遵循：

- 先把 `find_person` 打磨稳定
- 再扩展到 `search_knowledge`
- 最后扩展到 `summary`

不能一开始就三条链路同时大改，否则会放大调试成本，也容易影响现有稳定逻辑。

### 15.1 第一阶段：找人链路全面实现

这一阶段的目标，是把当前已经落地的找人闭环做成可持续调优的正式版本。

本阶段继续完善的重点包括：

- 把高频企业术语沉淀为稳定别名映射
- 让 `find_person` 的前置标注结果更可观测
- 让自检阶段对“证据强 / 弱 / 冲突”的判断更贴近真实业务
- 增加轻量澄清能力，用于处理特别泛的问题
- 补充针对大企业高频问题的回归样例

本阶段完成标志：

- 相近找人问法的结果方向稳定
- 重复消息和积压重复回复问题已被控制
- 文档优先原则在结果中稳定体现
- 弱证据场景不再轻易给出唯一负责人

### 15.2 第二阶段：扩展到知识检索链路

当找人链路稳定后，可以把同样的方法扩展到 `search_knowledge`。

这一阶段不是重写知识检索，而是只增强前置理解和后置自检。

目标是解决以下问题：

- 用户问题很泛，但系统直接拿裸 query 搜
- 用户真实想问的是“安装 / 流程 / 原理 / 职责总结”，但检索词没有区分
- 搜到了文档，但文档并没有真正回答问题
- 最终答案过于依赖命中数量，而不是命中质量

这一阶段建议引入的能力：

- 知识问答前置语义标注
- 检索意图分类
- 主实体 / 修饰实体拆分
- 通识问答兜底条件识别
- 检索后答案自检

本阶段必须遵守：

- 不破坏当前知识问答可用性
- 不改变 summary 十篇上限逻辑
- 不改变找人链路现有行为

### 15.3 第三阶段：扩展到总结链路

总结链路比普通知识问答更依赖“材料是否足够支撑结论”，因此也非常适合加入同样的闭环。

这一阶段主要解决：

- 搜到了几篇文档，但材料不足以支持“团队主要职责”这类总结
- 文档更多是技术材料，缺少业务映射
- 模型容易给出保守但不够可操作的归纳结果

这一阶段建议引入的能力：

- 总结目标识别
- 总结范围识别
- 技术实体与业务实体并行保留
- 总结结论自检
- 不足证据时自动降级为“现有材料能说明什么 / 还缺什么”

本阶段必须继续保持：

- 只在 `summary_mode=True` 下生效
- 十篇限制继续有效
- 不影响普通知识检索链路

### 15.4 全面实现前的推荐顺序

推荐的实施顺序如下：

1. 找人链路补齐企业术语映射与澄清策略
2. 找人链路补齐样例集与回归验证
3. 知识问答链路接入前置标注
4. 知识问答链路接入答案自检
5. 总结链路接入总结目标识别
6. 总结链路接入结论自检

这个顺序的核心原则是：

- 先做最影响 MVP 的链路
- 先做收益大、风险小的步骤
- 先控制理解质量，再扩展到总结质量

## 16. 全面实现前的需求对齐清单

- 正式职责依据文档列表

需要确认：

- 允许通识兜底的问题类型
- 不允许通识兜底的问题类型

### 16.3 总结链路

需要你给出的材料：

- 你认可的总结答案风格
- 典型“搜到了但不足以下结论”的案例

这三条链路在全面实现时，都必须共同遵守以下约束：

- 不能破坏现有稳定可用链路
- 不能因为引入 LLM 标注层而让响应时间不可控
- 不能让模型绕过代码直接决定数据源优先级
- 不能让自检层反向制造新的幻觉
- 不能改变你已经明确过的业务权重原则
